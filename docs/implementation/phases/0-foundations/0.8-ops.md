# 0.8 — Operación e infraestructura

## Objetivo

Producción segura, con backups probados y despliegues sin sorpresas.

## Depende de

Se hace en paralelo; obligatorio antes del primer deploy con datos reales.

## Alcance

- Vercel: proyectos `web` y `crm`; variables por entorno; revisar si el plan Hobby cubre el uso o hace falta Pro.
- Supabase: Data API desactivada, RLS, pooler (6543) para runtime, conexión directa para migraciones.
- Migraciones con `prisma migrate deploy` desde GitHub Actions al mergear en `main` (nunca en el build de Vercel, para que los previews no toquen producción).
- Backup diario: `pg_dump` cifrado a B2 privado, retención 30 días, restauración probada una vez por mes.
- Dominios: `crm.<dominio>`, `media.<dominio>`; cabeceras de seguridad de [`security.md`](../../architecture/security.md).
- Procedimiento documentado de rotación de secretos.
- **Archivos y multimedia (de la 0.6, se documentan acá y no se aprovisionaron):**
  - Buckets B2 `público` y `privado` y **una key de aplicación por bucket** con las capacidades mínimas
    (privado: `listBuckets`, `readFiles`, `writeFiles`, `deleteFiles`; público: `readFiles`,
    `writeFiles`, `deleteFiles`). Variables `S3_*` por entorno en Vercel.
  - CORS del bucket **privado** de B2 para `PUT` desde el origen del CRM (`crm.<dominio>`), con
    `Content-Type` permitido y `ETag` expuesto.
  - `media.<dominio>` en Cloudflare apuntando al bucket público, con caché largo e **inmutable** (las
    claves llevan el `fileId` y nunca cambian) y `MEDIA_PUBLIC_BASE_URL` apuntando ahí.
  - Cron en `apps/crm/vercel.json` (`/api/internal/media/purge`, una vez por día: Hobby no permite más)
    y `CRON_SECRET` (≥ 32 caracteres) en las variables de Vercel; Vercel lo envía como bearer.
  - Verificar que el proxy de producción sobrescribe `X-Forwarded-For` (la IP de auditoría).
  - Levantar el S3 local en el job de CI de la 0.7 (`docker compose up -d s3 s3-init`): los tests de
    `core/storage` y `modules/media` usan storage real.
