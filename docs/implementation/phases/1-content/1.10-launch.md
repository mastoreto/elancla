# 1.10 — Lanzamiento: operación, infraestructura y primer release

> Antes era la subfase **0.8**. Se movió al final de la fase 1 porque mergear a `main` publica la web
> y no se publica hasta tener el CRM de contenidos. Suma los pasos que quedaron pendientes de la 0.7
> (primer release, primer PR `develop → main`, protección de rama).

## Objetivo

Publicar la web y el CRM en producción de forma segura: backups probados, despliegues sin pasos
manuales y `main` protegido por el CI.

## Depende de

1.1 a 1.9 terminadas (1.8 galería diferida). 0.7 hecha (CI, Husky, versionado).

## Alcance

**Se puede hacer y verificar en local antes de crear cuentas:**

- Workflow de deploy: `prisma migrate deploy` desde GitHub Actions al mergear en `main`, con la
  conexión directa (`app_migrator`); nunca en el build de Vercel, para que los previews no toquen
  producción. Deploys de Vercel solo desde `main` (previews sin acceso a la BD de producción).
- Backup diario con cron de GitHub Actions: `pg_dump` → **cifrado con `age` a la clave pública**
  (versionada en el repo; la privada queda offline con el administrador del sistema) → bucket B2
  privado de backups, retención 30 días. Probado contra Docker local con SeaweedFS en lugar de B2.
- Restauración: script que baja un backup, lo descifra con la clave privada, lo restaura en una BD
  vacía y verifica (migraciones al día, conteos, invariantes de `schemaInvariants`). Recordatorio
  mensual (workflow programado que abre un issue "probar restauración").
- Escaneo de cabeceras de seguridad de CRM y web contra la tabla de
  [`security.md`](../../architecture/security.md) §4 (test automatizado sobre los builds locales).
  La web hoy no tiene HSTS, CSP ni COOP en `apps/web/vercel.json`: se agregan.
- Cron en `apps/crm/vercel.json` (`/api/internal/media/purge`, una vez por día: Hobby no permite más); agendar también `/api/internal/blog/views/purge` (borra los hashes de visitantes de días anteriores).
- Sermones (de la 1.7): cargar `YOUTUBE_API_KEY` en el entorno de la API y el `youtubeChannelId` del canal
  en Ajustes del sitio (el seed lo toma de `YOUTUBE_CHANNEL_ID`); correr `import:sermons` en producción
  (`bun run --filter @ancla/api import:sermons -- --org <slug> --playlist <id> --dry-run` primero) para
  traer el historial (el script está hecho en la 1.7a y es idempotente; necesita `YOUTUBE_API_KEY`, el
  `youtubeChannelId` y un usuario admin en la organización; ver [`1.7`](./1.7-sermons-podcasts.md)). El cron `/api/internal/platforms/refresh` (05:00) ya
  está en `apps/crm/vercel.json`.
- Runbooks en `docs/`: aprovisionamiento paso a paso y rotación de secretos (`BETTER_AUTH_SECRET`,
  credenciales de Postgres, keys de B2, `CRON_SECRET`, site keys, clave `age`).

**Aprovisionamiento (al lanzar, siguiendo el runbook):**

- Vercel: proyectos `web` y `crm`; variables por entorno; revisar si Hobby cubre el uso o hace falta Pro.
- Supabase: Data API desactivada, RLS, pooler (6543, `pgbouncer=true`) para runtime, conexión directa
  para migraciones; roles `app_migrator` y `app_runtime` (equivalente de `init-roles.sh`).
- Dominios: `crm.<dominio>`, `media.<dominio>`; cabeceras de `security.md`.
- **Archivos y multimedia (de la 0.6):**
  - Buckets B2 `público` y `privado` y **una key de aplicación por bucket** con las capacidades mínimas
    (privado: `listBuckets`, `readFiles`, `writeFiles`, `deleteFiles`; público: `readFiles`,
    `writeFiles`, `deleteFiles`). Bucket aparte para backups con su propia key (solo escritura desde
    Actions). Variables `S3_*` por entorno en Vercel.
  - CORS del bucket **privado** de B2 para `PUT` desde `crm.<dominio>`, con `Content-Type` permitido
    y `ETag` expuesto.
  - `media.<dominio>` en Cloudflare apuntando al bucket público, caché largo e **inmutable** (las
    claves llevan el `fileId`) y `MEDIA_PUBLIC_BASE_URL` apuntando ahí.
  - `CRON_SECRET` (≥ 32 caracteres) en Vercel; Vercel lo envía como bearer.
  - Verificar que el proxy de producción sobrescribe `X-Forwarded-For` (IP de auditoría y rate limit).
- Secretos de GitHub Actions: URL de migración, key del bucket de backups.

**Primer release y `main` (pendientes de la 0.7, en este orden, cada paso con confirmación):**

1. En `develop`: `bun run release:first` → `v0.1.0` + `CHANGELOG.md` (es el primero: incluye toda la
   historia; se puede resumir a mano antes del push).
2. `git push --follow-tags` y PR `develop → main`: primera corrida del CI (`source-branch`,
   `quality`, `db`, `test`, `e2e`, `version`) y primer deploy.
3. Protección de rama vía `gh api` (detalle en
   [`plans/0.7-testing-ci.md`](../../plans/0.7-testing-ci.md), verificación 9): `main` con los 6
   checks requeridos + 1 aprobación, sin force-push ni borrado; `develop` sin force-push ni borrado.

## Tests obligatorios

- Backup cifrado → restauración en una BD vacía, verificada (local y una vez en producción).
- Un backup no se puede leer sin la clave privada.
- Escaneo de cabeceras de seguridad de CRM y web.
- El workflow de deploy no corre migraciones en previews.

## Terminado cuando

- Backup y restauración probados.
- Deploy de `main` aplica migraciones y despliega sin pasos manuales.
- `v0.1.0` publicada, CI verde en el PR `develop → main` y `main` protegido.
