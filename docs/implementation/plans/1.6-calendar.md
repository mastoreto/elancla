# Plan — Fase 1.6: Calendario

## Contexto

La 1.6 (`docs/implementation/phases/1-content/1.6-calendar.md`, D-26, D-27, D-29, D-30, D-31) hace
del calendario la única fuente de horarios de culto, de actividades de ministerios y de eventos.
Estado de partida (tras el merge de la 1.5c en `develop`):

- **BD**: no hay modelos de calendario. `Organization.timezone` ya existe (IANA, seed
  `America/Montevideo`). `SiteSettings.serviceTimes Json` es el puente de la 1.3
  (`{ kind: worship|bibleSchool, weekday 0=domingo, start, end? }`, ponytail en `schema.prisma:103`).
  `EditorialContentType` = `BLOG_POST | MINISTRY | SIMPLE_PAGE`.
- **API**: sin rutas de calendario ni permisos `content.events` / `calendar.*`. `serviceTimes` sale
  por `toPublicSiteSettingsDto` (`modules/site/domain/parseServiceTimes`). Cron = rutas
  `GET /internal/...` con `requireCronSecret` (`modules/media`, `modules/blog/internal.routes.ts`);
  no hay `crons` en ningún `vercel.json`. Mail: `core/mail` (SMTP) + `packages/emails`.
- **Web**: calendario completo sobre `apps/web/src/data/calendar.ts` (mock 2027, colores hex,
  `day` 0=lunes): `pages/{,[locale]/}calendario-anual/`, `imprimir/[format].astro` (A3/A4/digital),
  `calendario-anual.ics.ts` (UID inestable, sin `SEQUENCE`/`STATUS`), `sections/calendar/**`.
  Los horarios llegan por `getSiteConfig().serviceTimes` → `buildSiteTokens` (Hero, Sunday,
  Closing, footer, Visítanos + `buildGeneratedFaqs`, `seo.ts` JSON-LD, `toOpeningHours`).
  `America/Montevideo` hardcodeado en `.ics`, `calendar.ts`, `seo.ts:151`, `SermonsPage.astro:49`.
  El ministerio no muestra "cuándo" (`buildMinistrySections`, `MinistryTemplate.astro:241-290`).
- **CRM**: sin rutas de calendario; card temporal `website/components/service-times-card/`.

## Ejecución (orquestador Sonnet 5.5)

siguiendo este plan **al pie de la letra**. Después Opus revisa el diff, corre todo local
(Docker/Kiri) y **cierra cada tramo con un PR a `develop` con tests en verde**, sin `Co-Authored-By`.

## Decisiones (confirmadas con el equipo / defaults)

| Tema | Decisión |
|---|---|
| Fechas y horas | Hora de pared de la iglesia, sin conversión a UTC: horas `"HH:mm"` (String), fechas `@db.Date`/`"YYYY-MM-DD"`. "Hoy" = fecha local en `Organization.timezone` vía `Intl.DateTimeFormat` (sin dependencias). `weekday` 0 = domingo en BD, contratos y API (igual que `serviceTimes`); la web convierte a lunes-primero en su util de grilla. |
| Conjuntos (`ScheduleSet`) | `{ id, organizationId, validFrom?, validTo? (@db.Date), isDefault, forcedActive, order, version, deletedAt }` + `ScheduleSetTranslation { name ≤60 }`. Un solo `isDefault` por org (índice único parcial en SQL). `forcedActive` es el "switch manual"; uno solo a la vez (índice parcial). |
| Resolución (función pura `resolveScheduleForDate`) | Para una fecha: **excepción de la fecha > conjunto con `forcedActive` > conjunto cuya vigencia cubre la fecha (si hay varios, el de vigencia más corta) > predeterminado**. Devuelve `{ set \| null, exception \| null }`. `resolveWeek(today)` resuelve los 7 días siguientes (incluye hoy) y es lo que alimenta horarios de culto y "cuándo". Tabla de casos en test. |
| Actividad recurrente | `RecurringActivity { id, organizationId, scheduleSetId, weekday, start, end?, placeId?, serviceKind? (enum WORSHIP \| BIBLE_SCHOOL; no nulo = "es horario de culto"), isPublic, isFixed, year Int?, annualReview, needsReview, version, deletedAt }` + traducción `{ title ≤80 }` + `RecurringActivityMinistry (activityId, ministryId)`. `CHECK`: `is_fixed = (year IS NULL)` y `annual_review → is_fixed`. Se editan **directo con auditoría** (también tras publicar el año). `serviceKind` en vez de un booleano para no perder la distinción culto/escuela bíblica que usan los tokens. |
| Excepción | `ScheduleException { id, organizationId, date @db.Date (único por org), replacementSetId? (→ ScheduleSet; nulo = "sin reunión"), version }` + traducción `{ message ≤200 }`. Directa con auditoría. |
| Lugares | `Place { id, organizationId, address?, mapsUrl? (https), order, version, deletedAt }` + traducción `{ name ≤80 }`. Borrar uno usado → 409 `place_in_use`. Eventos: `placeMode` `PLACE \| TBC \| EXTERNAL` (+ `externalAddress` ≤200). |
| `serviceTimes` | Se borra la columna, `parseServiceTimes`, el campo del DTO admin de `SiteSettings` y la card del CRM. El DTO **público** de settings conserva `serviceTimes` con la **misma forma**, calculado por la API desde las actividades públicas con `serviceKind` de `resolveWeek(hoy)` (fijas + del año si está publicado). Así Hero, Sunday, Closing, footer, Visítanos, JSON-LD y `buildGeneratedFaqs` no cambian. Se suma `timezone` al DTO público y la web deja de hardcodear `America/Montevideo`. `// ponytail: resolved per request; cache TTL (60s) makes midnight switches lag ≤1 min`. |
| Eventos | **Tipo editorial `event`** (snapshot como fuente, igual que blog/ministerio; sin `EventTranslation` ni `EventMinistry`, se actualiza la fase). Fila `Event { id, organizationId, year, visibility PUBLIC \| INTERNAL, sequence Int @default(0), liveAt?, needsReview, version }` + `EventAudienceRole (eventId, roleId)`. Snapshot: no traducible `startDate`, `startTime?`, `endDate?`, `endTime?`, `allDay`, `placeMode`, `placeId?`, `externalAddress?`, `ministryIds[]` (máx. 6; vacío = iglesia en general), `imageId?`, `linkUrl?` (https), `status SCHEDULED \| CANCELLED`; por idioma `title ≤120`, `description? ≤1000`. `beforeGoLive`: año del `startDate` = `Event.year` (409 `year_mismatch`), lugar/ministerios/imagen de la org (400 `invalid_place\|ministry\|media`), año publicado (409 `year_not_published`), `sequence += 1`, `liveAt = now`. Visibilidad y audiencia son columnas (config directa con auditoría). |
| Eventos internos | Nunca en la API pública ni en el `.ics`. En el CRM los ve quien tenga `calendar.internal:view` **y** un rol de su audiencia (el admin siempre). Para que las rutas `/editorial/event/:id/...` no filtren contenido, el registro editorial suma un hook opcional `entityVisibleTo?(tx, organizationId, entityId, access) → boolean` (falso → 404) que solo implementa `event`; los demás tipos no cambian. |
| Año (`CalendarYear`) | `{ id, organizationId, year (único por org), status DRAFT \| PUBLISHED, publishedAt?, publishedById? }`. Con el año en `DRAFT` los eventos solo guardan borrador (publicar uno suelto → 409 `year_not_published`). **Publicar el año** (`calendar.year:publish`) en una transacción: pasa a vivo cada revisión de trabajo de los eventos del año usando la primitiva de go-live del motor (el acto de publicar el año es la aprobación; no exige revisión obligatoria por evento) y marca el año `PUBLISHED`. Después: cada evento por el flujo de 1.2. Audit `calendarYear.published`. |
| Año a mostrar y cambio de año | Año actual = año de la fecha local en la zona de la org, por request. Público: actividades fijas públicas siempre; actividades del año y eventos solo si ese año está `PUBLISHED`. Año no publicado → solo fijas públicas. |
| Revisión anual | `ActivityYearReview { activityId, year, confirmedById, confirmedAt }` `@@unique([activityId, year])`. `POST /content/calendar/years/:year/reviews { activityId }` confirma (actividad fija con `annualReview`). |
| Copiar del año anterior | `POST /content/calendar/years/:year/copy { fromYear, activityIds[], eventIds[], keepExactDates }`: el CRM traduce la selección (tipo, ministerio, elemento) a ids y el servidor copia **exactamente** esos (ids ajenos al año origen → 400). Solo actividades no fijas y eventos. Lo copiado queda `needsReview = true` (los eventos como `Event` nuevo + revisión `DRAFT`). Fechas con `shiftDateKeepingWeekday(date, toYear)`: misma fecha en el año destino (29/2 → 28/2) y luego el mismo día de la semana más cercano (empate → el anterior); `keepExactDates` copia la fecha tal cual. Año destino debe existir en `DRAFT`. |
| Recordatorios | `CalendarReminderSettings { organizationId @unique, recipientRoleIds uuid[], recipientUserIds uuid[], lastSentOn? @db.Date }`. Pura `shouldRemind(localDate, state)`: desde el 1/12 del año Y, los días con `(díasDesde1/12) % 2 === 0` (1, 3, 5/12… y sigue en enero), mientras el año Y+1 no esté publicado **o** quede alguna actividad fija con `annualReview` sin confirmar para Y+1; idempotente con `lastSentOn`. Cron `GET /internal/calendar/reminders` (`requireCronSecret`), diario en `apps/crm/vercel.json` (`crons`, nuevo). Panel: `GET /content/calendar/pending`. |
| Permisos | Catálogo: `events` = `content.events` (`view`, `create`, `edit`, `delete`, `publish`; alcance `all`), `calendarInternal` = `calendar.internal` (`view`), `calendarYear` = `calendar.year` (`publish`). Horarios, lugares, excepciones, copia y revisión anual piden `events.edit`; recordatorios `events.edit`. Presets: `content-editor` recibe todo `events` + `calendarInternal.view` + `calendarYear.publish`. `leader` sin cambios. Rutas nuevas en `authzMatrix`. |
| Colores | El color de una actividad/evento es el `Ministry.color` (token) de su primer ministerio; sin ministerio → `DEFAULT_MINISTRY_COLOR`. La web lo pinta con `var(--color-<token>)`; se borran los hex de `calendar.ts`. |
| UID del `.ics` | `uid` = `<eventId>@<host>`: el DTO público del calendario expone `uid`, `sequence` y `lastModified` (`liveAt`). Es la única excepción a "sin ids internos" (RFC 5545 exige UID estable); se anota en la fase. |
