# Plan — Fase 1.1: API pública y SDK

## Contexto

La 1.1 (`docs/implementation/phases/1-content/1.1-public-api-sdk.md`, D-22, D-25, D-26,
`architecture/multi-site.md`, `architecture/security.md` §2) corta la dependencia directa de la web
con la BD: hoy `packages/content/src/site.ts` hace `db.siteSettings.findFirst()` en **cada request**
(vía `apps/web/src/middleware.ts`) y la web se buildea con `DATABASE_URL` y Prisma. Al terminar, la
web lee solo por `GET /api/public/v1/:churchSlug/...` con una **site key**, y no se cae si la API no
responde.

Hoy **solo `SiteSettings` sale de la BD**. Blog, ministerios y calendario son seeds en código y
pasan a la API en sus subfases (1.4, 1.5, 1.6). Por eso en la 1.1 la API pública expone solo
`settings`, y el SDK deja listo el cliente para que cada subfase agregue su endpoint.

**Ejecución: la implementación se hace con Sonnet 5.5** (`claude-sonnet-5-5`), siguiendo este plan
al pie de la letra. Después Opus revisa el diff, corre todo local y **cierra con PR a `develop` con
tests en verde**, sin `Co-Authored-By`.
**Rama:** `feat/public-api` desde `develop` (que ya tiene la 0.7, PR #78). Primer paso: copiar este
plan a `docs/implementation/plans/1.1-public-api-sdk.md`.
Nota: `git fetch`/`push` por SSH falla en esta máquina; se usa HTTPS con `gh` como credential helper
(`git -c credential.helper='!gh auth git-credential' -c url."https://github.com/".insteadOf="git@github.com:" …`).

## Decisiones (defaults, ajustables)

| Tema | Decisión |
|---|---|
| URL | `/api/public/v1/:churchSlug/...` (la API vive bajo `/api` en el CRM). Se documenta así en `multi-site.md` y `security.md`. |
| Endpoints públicos 1.1 | `GET /public/v1/:churchSlug/settings?locale=` y `GET /public/v1/openapi.json`. El resto (posts, events, ministries, sermons) lo suma cada subfase. |
| Formato de key | `sk_<keyId>_<secret>`: `keyId` = UUID del registro, `secret` = `randomBytes(32).toString("base64url")`. Se busca por id y se compara `sha256(secret)` con `timingSafeEqual`. En BD solo `secretHash`. El secreto se muestra **una vez**. |
| Permiso | `site:manage` no existe y `manage` no es una acción válida. Se agrega al catálogo `siteKeys: { resource: "site.keys", actions: ["view","create","delete"], scopes: ALL_ONLY, dangerous: ["create","delete"] }`. Rotar = crear la nueva + revocar la vieja. Se actualizan la fase 1.1 y `security.md`. |
| Rotación | Máximo **2 keys activas** por organización. Crear una tercera → 409 `site_key_limit`. Revocar = `revokedAt = now()` (no se borra; queda auditado). |
| 401 | Sin key, mal formada, inexistente, revocada, hash distinto o `churchSlug` ≠ slug de la organización de la key → **mismo** 401 Problem Details (sin detalle que distinga el caso). |
| Locale | `?locale=` opcional, regex `^[a-z]{2}(-[A-Z]{2})?$` (si no matchea → 400). Si no está en `Organization.locales` → `defaultLocale`. La respuesta trae `locale` con el idioma servido. Los textos traducibles caen al idioma por defecto si falta la traducción. |
| Caché | `Cache-Control: public, s-maxage=60, stale-while-revalidate=300`. `securityHeaders` solo pone `private, no-store` **si la ruta no puso `Cache-Control`**. Consecuencia aceptada: una key revocada puede seguir sirviendo desde el CDN hasta ~6 min (el contenido es público por naturaleza, security.md §2). |
| Rate limit público | **Ninguno en 1.1**: `rateLimit` se llavea por IP y aquí la IP es la del servidor web. `// ponytail:` en el guard → Vercel Firewall por ruta en 1.10, o un limit por `keyId` si hay abuso. |
| `lastUsedAt` | No se guarda (sería un write por request). Saltado. |
| OpenAPI público | Router propio (`createRouter()`) para el módulo `public`. `bun run openapi` además escribe `packages/contracts/openapi/public-v1.json`. Se sirve en `/api/public/v1/openapi.json` también en producción (es el contrato público). |
| Org en rutas públicas | El guard pone `ctx.organizationId` desde la key. El caso de uso usa `forOrganization(db, orgId)`. |
| SDK | `packages/content` **deja de depender de `@ancla/db`** y pasa a depender de `@ancla/contracts` (solo zod). Cliente `fetch` propio con zod en el borde. No se usa `hc` porque no hay que importar tipos de `apps/api` en la web. Timeout 2 s. |
| Caché del SDK | En memoria, TTL 60 s, con *last-known-good*: si la API falla, se sirve el último valor bueno o `SITE_FALLBACK`. Se registra `console.warn` como máximo una vez por ventana. Se mantiene la firma `getSiteConfig(): Promise<SiteConfig>`. |
| Env web | `API_URL`, `SITE_API_KEY`, `SITE_CHURCH_SLUG`, solo servidor (nunca `PUBLIC_`), leídos con `process.env` (el mismo patrón que `data/youtube.ts`). Si faltan → `SITE_FALLBACK` sin pegarle a la red. |
| Blog | Sigue con seeds. `// ponytail: phase 1.4 moves posts to /public/v1/:slug/posts`. Las firmas de `access.ts` no cambian. |
| UI de keys | Configuración (CRM) → pestaña nueva **"Sitio web"** (`siteKeys`, permiso `PERMISSIONS.siteKeys.view`) con una card "Claves del sitio": lista, crear (el diálogo muestra la key una vez con botón copiar y aviso de que no se vuelve a ver) y revocar (con confirmación). Convención de estilos de CLAUDE.md §4.8. |
| Key local | CLI `apps/api/src/scripts/createSiteKey/`, igual que `scripts/invite`: `bun run --filter @ancla/api site-key:create -- --name "web local"`. Imprime la key una vez para pegarla en `.env`. Se audita con `auditSourceForCli`. |

## 1. BD

- `schema.prisma`: modelo `SiteApiKey { id uuid(7), organizationId, name String, secretHash String, createdById String? (User, onDelete SetNull), createdAt, revokedAt DateTime? }`, `@@index([organizationId, revokedAt])`, `@@map("site_api_keys")`. Relación en `Organization` y `User`.
- Migración `site_api_keys` (`db:migrate`). Al final del SQL se copia el bloque de RLS y grants de las migraciones previas (ver `20261118233606_security_roles_rls` y `20261119180000_audit_log`): `ENABLE ROW LEVEL SECURITY` + policy `app_runtime_all` + `GRANT SELECT, INSERT, UPDATE ON site_api_keys TO app_runtime` (sin `DELETE`).
- Agregar `SiteApiKey` a `TENANT_MODELS` (`apps/api/src/core/tenancy/tenantModels/tenantModels.ts`); el test de paridad lo exige.
- Seed: si los roles del seed (`packages/db/prisma/seed/`) reciben permisos por lista, dar `siteKeys:*` a `admin`.

## 2. Contratos (`packages/contracts`)

- `authz/permissionCatalog`: entrada `siteKeys` (tabla de arriba).
- `audit/auditActions.ts`: grupo `siteApiKey: { created, revoked }`.
- `siteKeys/`: `siteKeyDto { id, name, hint ("sk_" + primeros 8 del id + "…"), createdAt, revokedAt|null }` (`.strict()`), `createSiteKeyBody { name: 1..60 }`, `createdSiteKeyDto = siteKeyDto + { key }`.
- `public/`: `publicSiteSettingsDto` (`.strict()`): `locale, name, shortName, subtitle, url, status ("online"|"maintenance"|"closed"), contactEmail, address {street, city, region, country, postalCode}, geo {latitude, longitude}|null, themeColor, founded, serviceTimesSummary, social {website, instagram, youtube, facebook, twitter, spotify, linkedin}, about (string|null)`. Los nullables, explícitos. **Ni ids, ni `version`, ni timestamps.**
- Re-exportar desde `src/index.ts`.

## 3. API (`apps/api`)

- `core/http/securityHeaders`: `if (!c.res.headers.has("Cache-Control")) set("private, no-store")`, con su test (las rutas autenticadas siguen con `no-store`).
- Mover los helpers de token a `core/crypto/` (`generateSecret`, `sha256Hex`, `safeEqualHex`) y reusarlos desde `invitationToken` y `requireCronSecret`. Solo si el diff queda chico; si no, el guard nuevo importa `invitationToken` y se deja así.
- **`modules/siteKeys/`** (plantilla: `identity/invitations`):
  - `GET /site-keys` (`siteKeys:view`), `POST /site-keys` (`siteKeys:create`, 201 con `createdSiteKeyDto`, 409 si ya hay 2 activas), `DELETE /site-keys/:id` (`siteKeys:delete`, 204; 404 si no es de la org o ya está revocada).
  - Las use cases `createSiteKey` y `revokeSiteKey` corren en `withTransaction` + `writeAudit` (`before`/`after` sin `secretHash`). El conteo de activas y el insert van en la misma transacción.
  - Mapper `toSiteKeyDto`. Domain `siteKeyToken` con `formatKey(id, secret)` y `parseKey(raw) → {id, secret} | null` (puro, con test).
- **`modules/public/`**:
  - `guards/requireSiteKey`: envuelto en `declareAccess`. Lee `Authorization: Bearer`, hace `parseKey`, busca la key por id con `organization.slug`, chequea `revokedAt === null`, `safeEqual(sha256(secret), secretHash)` y `slug === c.req.param("churchSlug")`, y deja `ctx.organizationId`. Cualquier fallo → `UnauthorizedError` (mismo cuerpo). `// ponytail:` sin rate limit (ver Decisiones).
  - `useCases/getPublicSiteSettings(orgId, locale)`: lee org (`defaultLocale`, `locales`) + `siteSettings` + traducciones de `[locale, default]`, resuelve el fallback y mapea con `toPublicSiteSettingsDto`. 404 si la org no tiene settings.
  - `public.routes.ts`: `GET /:churchSlug/settings` con `middleware: [requireSiteKey]`, que responde con `c.header("Cache-Control", PUBLIC_CACHE_CONTROL)`. Router montado en `app.ts` como `.route("/public/v1", publicRoutes)`. `GET /openapi.json` del documento público con `allowPublic`.
- `authzMatrix.test.ts`: `PUBLIC_ROUTES` suma `"/api/public/v1/openapi.json"` y `"/api/public/v1/:churchSlug/*"` (las cubre su propio test de 401). Filas de matriz para `/site-keys` (anónimo → 401, sin rol → 403, con permiso → 2xx).
- `scripts/generateOpenApi`: genera también `public-v1.json`. `scripts/createSiteKey/` + script en `apps/api/package.json`.

## Tests obligatorios (todos en `apps/api/src/modules/public/public.routes.test.ts` y `siteKeys.routes.test.ts`)

1. Sin `Authorization`, bearer mal formado, id inexistente, secreto incorrecto, key revocada, key de otra iglesia con su slug cruzado → **401**, y el cuerpo es idéntico en todos los casos.
2. Key válida → 200; `publicSiteSettingsDto.strict().parse(body)` pasa, el body **no** tiene `id`, `organizationId`, `version`, `secretHash` ni timestamps; `Cache-Control` es el público.
3. `?locale=pt` sin traducción pt → `about` en `es` y `locale: "es"`. Locale inválido (`?locale=xx_yy`) → 400.
4. Site keys: el `POST` devuelve `key` y el `GET` nunca la devuelve (ni el hash). Tercera activa → 409. `DELETE` → la key deja de autenticar (401) y queda la fila de audit `siteApiKey.revoked` con el mismo `requestId`. La key de otra organización → 404.
5. Una ruta autenticada sigue devolviendo `Cache-Control: private, no-store`.
6. Unit: `parseKey`/`formatKey`; SDK (sección 5).
7. Matriz: filas de `/site-keys`. El test de cobertura de rutas sigue verde.

## Setup local y pantallas de estado

- **Setup local en un paso:** `bun run --filter @ancla/api site-key:create -- --name "web local" --write-env`
  crea la key y escribe `API_URL` (por defecto `http://localhost:3000`, `--api-url <origen>` lo cambia),
  `SITE_API_KEY` y `SITE_CHURCH_SLUG` en el `.env` raíz (reemplaza las líneas existentes o las agrega;
  no toca nada más ni imprime la key). Reiniciar `bun run dev`. Sin esas variables la web sirve
  `SITE_FALLBACK` y ahora lo avisa con un `console.warn` (una vez por proceso) que nombra las
  variables que faltan y este comando: antes, cambiar el estado en el CRM "no hacía nada" sin pista.
- **Estado del sitio en la web:** `maintenance` → pantalla "Mantenimiento" y `closed` → "Fuera de línea"
  (diseño "obra"; `apps/web/src/components/SiteStatusScreen/`). Mientras el sitio no está `online` las
  páginas HTML responden **503** con `Retry-After: 300`, `X-Robots-Tag: noindex` y `<meta robots noindex>`
  (`middleware.ts` + `utils/markSiteOffline`). "Ver horarios de culto" salta al bloque de horarios
  (`#horarios`, de `SiteConfig.serviceTimes`); el contacto es `mailto:` (no hay WhatsApp en
  `SiteSettings`); "Reintentar" recarga la página. No se muestran ventana horaria, avance ni cuenta
  regresiva del diseño porque no hay dato real detrás.
- **E2E:** Playwright levanta también la web (`apps/web/dist/server/entry.mjs`, puerto 4398) con la
  key fija de `.env.test` (`seed:e2e` la registra) y `SITE_CONFIG_TTL_MS=500`
  (variable opcional que acorta el caché del SDK; por defecto 60000). `siteStatus.spec.ts` cambia el
  estado desde el CRM y comprueba la web; `siteKeys.spec.ts` nunca revoca esa key. El job `e2e` de CI
  construye la web antes de Playwright.
