# Plan — Fase 1.2: Flujo editorial

## Contexto

La 1.2 (`docs/implementation/phases/1-content/1.2-editorial-workflow.md`, D-09, D-10, D-30) define un
único flujo de borrador → revisión → publicación para el contenido editable. Hoy **no hay contenido
editable real**: blog y ministerios del CRM son maquetas con seeds, y llegan en la 1.4 y la 1.5.

**Decisión del equipo:** la 1.2 deja el motor **montado y testeado, sin aplicarlo todavía** a ningún
contenido. Blog (1.4) y ministerios (1.5, los carga cada líder) lo adoptan en su fase. El flujo
también es una herramienta de auditoría y evaluación: todo queda en historial y en `AuditLog`.
Notificaciones: email + una bandeja "pendientes" en la app que se deriva de las revisiones (sin
tabla `Notification`).

**Ejecución:** implementa **Sonnet 5.5** (`claude-sonnet-5-5`) siguiendo este plan al pie de la
letra. Después Opus revisa el diff, corre todo local y **cierra con PR a `develop` con tests en
verde**, sin `Co-Authored-By`.
**Rama:** `feat/editorial-workflow` desde `develop` (ya tiene la 1.1, PR #80). Primer paso: copiar
este plan a `docs/implementation/plans/1.2-editorial-workflow.md`.
Nota: `git fetch`/`push` por SSH falla en esta máquina. Usar HTTPS con `gh` como credential helper:
`git -c credential.helper='!gh auth git-credential' -c url."https://github.com/".insteadOf="git@github.com:" …`.

## Decisiones (defaults, ajustables)

| Tema | Decisión |
|---|---|
| Tipos de contenido | Enum Prisma `EditorialContentType { BLOG_POST MINISTRY }`. En la URL van como `blog-post` y `ministry`. Cada tipo nuevo suma un valor al enum con su migración. |
| Registro de tipos | `apps/api/src/modules/editorial/registry/editorialTypes.ts`: por tipo guarda `{ permissions: { view, edit, publish }, snapshotSchema, ministryScoped, crmPath(entityId) }`. `BLOG_POST` usa `PERMISSIONS.blogPosts.*`, `ministryScoped: false` y `crmPath` `/blog`. `MINISTRY` usa `PERMISSIONS.ministryProfile.*`, `ministryScoped: true` y `crmPath` `/ministries/:id`. `snapshotSchema` = `z.record(z.string(), z.unknown())`, con `// ponytail: 1.4/1.5 replace it with the real content schema`. |
| Modelo | Las revisiones son el contenido: el snapshot JSON del borrador vive en `ContentRevision`. El "publicado" de una entidad es su revisión `PUBLISHED`/`PAUSED`. Cada entidad tiene como máximo **una revisión de trabajo** (`DRAFT`/`IN_REVIEW`/`CHANGES_REQUESTED`) y **una en vivo** (`PUBLISHED`/`PAUSED`). Lo garantizan índices únicos parciales en SQL, no el código. |
| Estados | `DRAFT, IN_REVIEW, CHANGES_REQUESTED, PUBLISHED, PAUSED` (D-30), más `SUPERSEDED`: es interno, para la revisión en vivo anterior cuando se publica una nueva. El historial no se borra. |
| Lectura pública | El módulo exporta `findLiveSnapshot(orgId, type, entityId)` y `listLiveSnapshots(orgId, type)` (solo `PUBLISHED`, nunca `PAUSED`). En 1.4/1.5 la API pública lee de ahí o materializa columnas al publicar: lo decide esa fase. |
| `entityId` | Es un UUID cualquiera. En 1.2 no se valida que la entidad exista (no hay tablas todavía); `// ponytail:` 1.4/1.5 agregan el chequeo. |
| Permisos | Se suma la acción `publish` a `PERMISSION_ACTIONS`. Entrada nueva `blogPosts: { resource: "content.posts", actions: ["view","create","edit","delete","publish"], scopes: ALL_ONLY }`. `ministryProfile` suma `publish`. Entrada nueva `editorial: { resource: "editorial", actions: ["view","edit"], scopes: ALL_ONLY, dangerous: ["edit"] }`: en la fase se llamaba `editorial:configure`, pero `configure` no es una acción válida. **No** se crea `content:review`: quién revisa sale de `EditorialSettings` (pedido de la fase: "solo los revisores configurados pueden aprobar"). |
| Presets | `content-editor`: todo `blogPosts` + `ministryProfile.publish` (all). `leader` no cambia: tiene `ministryProfile` view/edit con alcance `ministry`, así que no puede publicar y su contenido siempre va a revisión. Como el seed no actualiza roles existentes, una migración de datos hace el backfill (el mismo patrón que `audit_log` con `auditor`). |
| Alcance ministerio | Si el tipo es `ministryScoped` y la concesión del usuario tiene alcance `ministry`, el `entityId` tiene que estar en `ctx.access.ministryIds`. Si no → 403. |
| Revisores | `EditorialSettings` por organización y tipo: `reviewerRoleIds[]`, `reviewerUserIds[]`, `mandatoryReviewRoleIds[]`, `mandatoryReviewUserIds[]` (arrays `uuid`). Es revisor el admin, o un usuario listado, o quien tenga un rol listado. Al guardar se valida que los ids sean de la organización (400). Los ids viejos (rol o usuario borrado) no matchean y se filtran al leer. `// ponytail: arrays, not join tables; move to FKs if stale ids ever matter`. |
| Auto-aprobación | Nadie aprueba ni pide cambios sobre su propia revisión, tampoco el admin → 403 `self_review`. Si no, la revisión obligatoria no sirve. |
| Publicar directo | Requiere `publish` del tipo **y** que el autor no esté en revisión obligatoria (por usuario o por cualquiera de sus roles). Si no → 403 (`publish_forbidden` / `review_required`). Reanudar algo pausado también exige `publish`, pero no la revisión obligatoria: ese contenido ya fue aprobado. |
| Conflictos | Cada transición actualiza con `where: { id, state: <estado esperado> }`. Si `count === 0` → 409 `invalid_transition`. Una violación de índice único (P2002) también → 409. |
| Retirar de revisión | Fuera de alcance (no está en la fase). `// ponytail:` agregar `withdraw` IN_REVIEW→DRAFT si se pide. |
| Notificaciones email | Después del commit, best-effort: si falla, se loguea con `console.error` y no rompe la request. `submit` → revisores del tipo menos el autor (si no hay ninguno configurado → los admins de la organización). `approve`/`requestChanges` → el autor (con el comentario). Plantilla `NoticeEmail` existente + un helper `renderEditorialNoticeEmail` en `packages/emails`. Textos en español (el CRM es solo español). El link es `CRM_ORIGIN + crmPath`. |
| Bandeja | `GET /editorial/inbox` (cualquier sesión): `toReview` (revisiones `IN_REVIEW` de tipos donde soy revisor y no soy autor) y `changesRequested` (mis revisiones `CHANGES_REQUESTED`). La campana del header la muestra. |
| Auditoría | Cada transición y cada cambio de configuración, en la misma transacción. `before`/`after` = resumen de la revisión (id, número, estado, autor), **sin** el snapshot. |

## 3. API (`apps/api/src/modules/editorial/`, plantilla: `siteKeys`)

- **`domain/editorialMachine/`** (puro, con test de tabla completa):
  - `nextState(state | null, action): EditorialState | null` con esta tabla:
    - `saveDraft`: ∅/DRAFT/CHANGES_REQUESTED → DRAFT
    - `submit`: DRAFT → IN_REVIEW
    - `publish`: DRAFT → PUBLISHED
    - `approve`: IN_REVIEW → PUBLISHED
    - `requestChanges`: IN_REVIEW → CHANGES_REQUESTED
    - `pause`: PUBLISHED → PAUSED
    - `resume`: PAUSED → PUBLISHED
    - El resto → `null`.
  - Cuando una revisión de trabajo pasa a PUBLISHED, la revisión en vivo anterior pasa a SUPERSEDED (lo hace el caso de uso en la misma transacción).
- **`domain/availableActions/`** (puro, con test): recibe `{ working, live, canEdit, canPublish, mustReview, isReviewer, isAuthor }` y devuelve las acciones que el usuario puede ejecutar ya (pasa `nextState` y los permisos). El CRM solo pinta lo que devuelve: no reimplementa reglas.
- **`domain/resolvePublishPath/`** (puro): `(canPublish, mustReview) → "direct" | "reviewOnly"`.
- **`registry/editorialTypes.ts`** (ver Decisiones) y un mapeo param ↔ enum.
- **`guards/requireEditorialPermission(kind: "view"|"edit"|"publish")`**: envuelto en `declareAccess` igual que `requirePermission`. Toma `:type` del registro y su permiso, aplica la regla de alcance ministerio y responde 404 si el tipo es desconocido.
- **`data/`**: repositorio de revisiones y settings (todo vía `forOrganization`), `findLiveSnapshot` y `listLiveSnapshots` (exportados desde el barrel del módulo para 1.4/1.5), y `resolveReviewers(tx, orgId, type)` / `isReviewer` / `mustReview(user)`. Estas resuelven los roles del usuario con `UserRole`.
- **`useCases/`**: `getEditorialStatus`, `saveDraft` (crea con `number = max+1` o actualiza el snapshot de la de trabajo), `submit`, `publish` (directo o resume), `approve`, `requestChanges`, `pause`, `listHistory`, `getInbox`, `getEditorialSettings`, `updateEditorialSettings`. Las mutaciones van en `withTransaction` + `writeAudit`, y las que notifican reciben el `mailer` como parámetro (igual que `createInvitation`).
- **`notifications/notifyEditorial.ts`**: arma los destinatarios y manda los emails después del commit (best-effort).
- **Rutas** (`editorial.routes.ts`, montadas en `app.ts`):

  | Método y ruta | Guard |
  |---|---|
  | `GET /editorial/{type}/{entityId}` | view |
  | `GET /editorial/{type}/{entityId}/history` | view |
  | `PUT /editorial/{type}/{entityId}/draft` | edit |
  | `POST …/submit` | edit |
  | `POST …/publish` | publish |
  | `POST …/pause` | publish |

  `resume` no tiene ruta propia: `publish` sobre una entidad sin revisión de trabajo y con la revisión en vivo `PAUSED` reanuda. Las rutas de acción responden `200` con `editorialStatusDto`.

## Tests obligatorios

En `apps/api/src/modules/editorial/editorial.routes.test.ts` y en los tests de dominio:

1. **Tabla de transiciones** (unit): cada estado × cada acción; las válidas dan el estado esperado y el resto `null`. En HTTP, una transición inválida → 409 (p. ej. `approve` sobre DRAFT, `submit` sobre IN_REVIEW, `pause` sin nada en vivo).
2. Sin `publish`, publicar directo → 403. El mismo usuario puede `submit`.
3. Autor con revisión obligatoria (por usuario y, en otro caso, por rol) → publicar directo 403 aunque tenga `publish`, y `availableActions` no incluye `publish`.
4. Editar contenido publicado: `saveDraft` + `submit` sobre una entidad con revisión en vivo → `findLiveSnapshot` sigue devolviendo el snapshot viejo. Después de `approve` devuelve el nuevo, y la anterior queda `SUPERSEDED`.
5. Solo los revisores configurados aprueban: un usuario con `publish` que no es revisor → 403. Un revisor por rol → 200. El autor revisor sobre su propia revisión → 403.
6. `requestChanges` sin comentario → 400. Con comentario → CHANGES_REQUESTED. Editar → DRAFT. La bandeja del autor lo lista mientras está en CHANGES_REQUESTED.
7. `pause` → `findLiveSnapshot` devuelve `null` y `listLiveSnapshots` no la incluye. `publish` (resume) la vuelve a mostrar.
8. Cada transición deja su fila de `AuditLog` (`editorial.*`) con el mismo `requestId`, y el `after` no trae `snapshot`.
9. Emails: `submit` manda a los revisores (no al autor). Sin revisores configurados va a los admins. `approve`/`requestChanges` mandan al autor. Un mailer que falla no rompe la request (`recordingMailer` / mailer que tira).
10. Alcance ministerio: un líder edita el ministerio suyo (200) pero no otro (403).
11. Settings: ids de otra organización → 400. `editorial:edit` requerido. Fila de audit `editorial.settingsUpdated`.
12. Índice parcial: dos `saveDraft` concurrentes sobre una entidad nueva → una 200 y otra 409 (o ambas terminan en la misma revisión), nunca dos revisiones de trabajo.
13. Matriz authz: filas de todas las rutas nuevas. El test de cobertura de rutas sigue verde.
14. Unit: `availableActions`, `resolvePublishPath`, `stateLabels` (CRM), render del email.
