# Plan — Fase 0.5: auditoría

## Contexto

0.4 dejó el RBAC y marcó cada mutación con `// ponytail: 0.5 adds writeAudit(tx, ...)`. La 0.5
(D-10, RF-05) agrega el registro append-only de todo lo que pasa: `AuditLog` escrito **en la misma
transacción** que la mutación, eventos de auth, denegaciones y un `GET /audit` de solo lectura con
pantalla en Configuración. Es la base de las fases siguientes (movimientos, informes, votaciones
llaman a `writeAudit` desde el día uno).

Este plan fue revisado contra el código por Opus 5.5; las correcciones ya están incorporadas.

**Ejecución: la implementación se hace con Sonnet 5.5** (`claude-sonnet-5-5`), siguiendo este plan
al pie de la letra. Después Opus revisa el diff, corre los tests, prueba en el navegador (Docker
local) y **cierra con PR a `develop` con tests en verde**, sin `Co-Authored-By`.
**Rama:** `feat/audit` desde `develop` (si `refactor/permission-references` no se mergeó, sale de ahí
y se rebasea). Primer paso: copiar este plan a `docs/implementation/plans/0.5-audit.md`.

## Decisiones (defaults, ajustables)

| Tema | Decisión |
|---|---|
| Actor | `actorId` **sin FK** + `actorLabel` (email al momento del hecho): el log sobrevive al borrado del usuario y los `cleanup()` de tests siguen funcionando. |
| Organización | FK `organizationId` con **`onDelete: Restrict`** (un cascade borraría el log aunque `app_runtime` no tenga `DELETE`: las acciones referenciales corren con privilegios del dueño). Test que lo verifica. |
| Inmutabilidad | `REVOKE UPDATE, DELETE, TRUNCATE` a `app_runtime` + RLS solo con policies `SELECT`/`INSERT`. El control real es el privilegio (RLS sin policy de UPDATE actualiza 0 filas en silencio). Sin triggers ni hash-chain. |
| Política de fallo | **Mutaciones: estrictas** (auditoría en la misma tx; si falla, todo falla). **Denegaciones y eventos de auth: best-effort** (`try/catch` + `console.error` estructurado con `requestId`; un fallo del log no convierte un 403 en 500 ni rompe un login ya hecho). Se documenta en D-10. |
| Lecturas sensibles | Se entrega el mecanismo (`writeAudit` sirve para `*.read`/`*.exported`); hoy no hay documentos privados ni informes, cada módulo futuro las cablea. Leer `GET /audit` no se audita. |
| Permiso | Nuevo recurso `audit` (solo `view`, alcance `all`). Admin implícito; **migración de datos** que agrega `audit:view` al rol `auditor` existente (el seed hace `update: {}`, no lo alcanzaría; mismo patrón que `rbac/migration.sql`). |
| Redacción | `before`/`after` son **DTOs** (`toRoleDto`, `toInvitationDto`: sin `tokenHash`); `redact()` es defensa en profundidad con lista exacta: `password`, `newPassword`, `currentPassword`, `token`, `tokenHash`, `secret`, `backupCodes`, `totpURI` (no `code`: borraría códigos de moneda/`MOV-…`). |
| IP | `ip` guarda `null` si no hay (no el centinela `"unknown"`). Se confía en el primer salto de `X-Forwarded-For` hasta 0.8: documentado en `security.md`. `requestId` es de correlación, no de confianza. |
| PII | `actorLabel` y el email de logins fallidos quedan sin poder borrarse; se documenta retención y tensión con supresión en D-10. |
| i18n CRM | Desviación aceptada: etiquetas en `data/` (el CRM aún no tiene i18n). |
| Orden | `orderBy: { id: "desc" }` (UUIDv7 ordena por tiempo); cursor por `id` con `toPage`. |

## Cambios de BD (`packages/db`)

- `AuditLog` → `audit_logs`: `id` (UUIDv7), `organizationId` (FK Restrict), `createdAt`,
  `actorId uuid?`, `actorLabel String?`, `action String`, `entityType String?`, `entityId String?`,
  `before Json?`, `after Json?`, `reason String?`, `outcome` enum `success | denied | failure`,
  `ip String?`, `userAgent String?`, `requestId String?`, `metadata Json?`.
- Índices: `(organizationId, createdAt)`, `(organizationId, entityType, entityId)`,
  `(organizationId, actorId)`.
- Migración nueva: tabla/enum; **redefine `app_secure_tables()`** con un `CONTINUE` para una lista de
  tablas solo-inserción (`audit_logs`) en vez de pisarles la policy; crea `app_runtime_select` y
  `app_runtime_insert`; revoca `UPDATE/DELETE/TRUNCATE`; INSERT de `role_permissions` `audit:view`
  para el rol `auditor` de cada organización; termina con `SELECT public.app_secure_tables()`.
- `schemaInvariants.test.ts`: la invariante usa `has_table_privilege('app_runtime','audit_logs',
  'UPDATE'|'DELETE'|'TRUNCATE')` = false y comprueba que no exista `app_runtime_all` en `audit_logs`
  (protege contra un `GRANT … ON ALL TABLES` copiado en una migración futura).
- `TENANT_MODELS` está en `apps/api/src/core/tenancy/tenantModels/tenantModels.ts`: agregar `AuditLog`.
- `resolveOrganizationId`: agregar `orderBy: { createdAt: "asc" }` (hoy `findFirst` sin orden).

## API (`apps/api`)

**`src/core/audit/`** (cada unidad en su carpeta con test y barrel):
`writeAudit/`, `redact/`, `auditSource/`, más `index.ts`.
- `AuditSource = { organizationId, actor: {id,label} | null, requestId, ip, userAgent }`.
- `writeAudit(client, source, event)`: `client` = `Prisma.TransactionClient | PrismaClient`;
  `event = { action, entity?, before?, after?, reason?, outcome?, metadata? }`.
- `auditSourceFrom(ctx)` (rutas/use cases) y `auditSourceFromHeaders(headers, actor?)` (hooks de Better
  Auth, CLI y `markInvitationAccepted`, que no tienen `RequestContext`).
- `RequestContext` suma `ip` y `userAgent`. Extraer `clientAddress` de `core/http/rateLimit` a
  `core/http/clientAddress/` (con barrel) y reusarla; `contextMiddleware` la llena.
- `authRouter` clona el `Request` agregando `X-Request-Id` (hoy pasa `c.req.raw` sin el id generado);
  `acceptInvitation` pasa `headers` a `signUpEmail`.

**Refactor previo para poder auditar en la misma tx:**
- Repos reciben `tx`: `findRoleRow` (hoy usa `db` global y dentro de la tx devolvería el estado
  anterior), repos de invitaciones (hoy `forOrganization(db, …)`, que exige `PrismaClient`),
  `replaceUserMinistries` (hoy `$transaction([...])` por lotes).
- `updateRole`: leer `before` **dentro** de la tx y con `lockRole`; `after` desde `tx`.
- `setUserRoles`: leer los roles previos para el `before`.
- `createInvitation`/`resendInvitation`/`revokeInvitation` pasan a `withTransaction`; el correo
  (`sendInvitationEmail`) queda **fuera y después** del commit.

**Cablear mutaciones** (borrar los `ponytail: 0.5`): `createRole`, `updateRole`, `deleteRole`,
`setUserRoles`, `setUserMinistries`, `createInvitation`, `resendInvitation`, `revokeInvitation`,
`markInvitationAccepted` (actor = usuario nuevo), `createPassword` (`POST /me/password`).
Invitaciones por CLI (`scripts/invite/invite.ts` → `issueInvitation`, `invitedById: null`): se audita
en `issueInvitation` con actor `{id: null, label: "cli"}`, así no se escapan las de consola.
`reason` (RF-05) viaja cuando el use case lo recibe.

**Denegaciones:** se registran en **`errorHandler`** (`core/errors/errorHandlers`, `onError` async)
para todo `ForbiddenError` (`metadata: { message, path }`): cubre `requirePermission`, policies de
roles/users, `assertCanAssignRoles`, `createInvitation` y `requireFreshSession` de una vez, y corre
cuando la tx de negocio ya hizo rollback. Best-effort.

**Auth:** plugin `auditHooks()` (patrón `roleSessionPolicy`), registrado **último** en `createAuth`.
Verificado contra Better Auth 1.7.25: el hook `after` **sí corre** con errores (`APIError` queda en
`ctx.context.returned`), pero la clasificación es:
- éxito = `newSession` presente; con 2FA pendiente `newSession` es `null` → `auth.login.twoFactorRequired`;
- fallo = status ≥ 400 **solo** en `/sign-in/email`, `/two-factor/verify-*`, `/reset-password`
  (`/callback/:id` usa 302 tanto en éxito como en error: no se clasifica por status);
- 2FA enabled/disabled vía `databaseHooks.user.update.before` (detectar `twoFactorEnabled` en `data`;
  el flag se activa en el primer `verify-totp`, no en `/enable`);
- reset completado con `emailAndPassword.onPasswordReset`; solicitado con `sendResetPassword`;
- también `change-password`, link de cuenta social y `verify-backup-code`.
El email intentado va en `metadata`, nunca la contraseña. Un fallo del log aquí se captura (best-effort).

**Módulo `modules/audit/`** (`data/ mappers/ useCases/ audit.routes.ts`, barrel): `GET /audit` con
`requireSession` + `requirePermission(PERMISSIONS.audit.view)`, filtros del query, `orderBy id desc`,
`toPage`, filtrado por organización. Registrar en `app.ts`.

## Tests obligatorios (bun test, Postgres real)

- Privilegios (`has_table_privilege`) y ausencia de `app_runtime_all`; `INSERT`/`SELECT` ok,
  `UPDATE`/`DELETE` fallan con `app_runtime`; borrar la organización falla (Restrict).
- Atomicidad con disparador natural: `updateRole` con nombre duplicado (`P2002` dentro de la tx) ⇒
  no queda fila; commit ⇒ queda con before/after correctos (el `after` refleja el estado nuevo).
- Denegación: un 403 deja `permission.denied` con actor, IP, UA y `requestId`; si el insert del log
  falla, la respuesta sigue siendo 403.
- Cada use case cableado deja su evento (en su `*.routes.test.ts`), con secretos redactados; incluye
  `issueInvitation` por CLI y `POST /me/password`.
- Auth e2e: login ok, login fallido (email desconocido y clave errónea, sin la clave en la fila),
  2FA pendiente, fallo de 2FA, reset completado.
- `GET /audit`: matriz de permisos (401/403/200), filtros, paginación; aislamiento por organización a
  nivel de repositorio (no crear una segunda organización en la BD compartida).
- Unitarios: `redact`, `auditSourceFrom*`, `clientAddress`.
- Los tests identifican sus filas por email/`requestId` únicos; el log solo se vacía con `db:reset`.
