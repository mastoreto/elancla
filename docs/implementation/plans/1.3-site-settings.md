# Plan — Fase 1.3: Sitio institucional

## Contexto

La 1.3 (`docs/implementation/phases/1-content/1.3-site-settings.md`, D-25, D-26, D-28, D-33, D-38,
D-39, D-40, D-41) busca que **ningún dato de la iglesia esté escrito en `apps/web`** y que la
información institucional se edite desde el CRM. Estado de partida en `develop`:

- La 1.1 dejó la API pública (`GET /api/public/v1/:churchSlug/settings`), las site keys y el SDK
  (`packages/content/src/site.ts`, caché de 60 s con last-known-good + `SITE_FALLBACK`).
- La 1.2 dejó el motor editorial (`apps/api/src/modules/editorial`) **sin adoptar todavía**. La 1.3
  lo adopta para las páginas simples.
- El CRM `/website` escribe la BD **directo** con server actions (`website/actions.ts`, permiso
  `content.edit`) y sin auditoría. Tiene estado, redes y un editor "Sobre nosotros"
  (`aboutRichText`) que la web **no muestra** en ningún lado (D-39: Nosotros es fijo).
- La 1.6 (calendario) no existe: los horarios están en `SiteSettings.serviceTimesSummary`
  (`"Su 11:15-13:00"`) y en un montón de textos i18n.
- Datos de la iglesia escritos a mano en la web: dirección, email, horarios, handles y dominio en
  `i18n/messages/{es,en,pt}/` (`landing`, `home`, `nav`, `visit`, `footer`, `content-pages`,
  `sermons-page`), el equipo de Nosotros en `content-pages.json` y las FAQ en `visit.json`.

**Ejecución:** **Sonnet 5.5** (`claude-sonnet-5-5`) orquesta cada tramo y reparte el trabajo en
workers por capa (API, web + SDK, CRM) siguiendo este plan al pie de la letra. Después Opus revisa el
diff, corre todo local (Docker/Kiri) y **cierra cada tramo con un PR a `develop` con tests en verde**,
sin `Co-Authored-By`.
**Entrega en 4 tramos secuenciales** (cada uno es una rama y un PR a `develop`, y el siguiente sale
de `develop` **después** del merge del anterior):

| Tramo | Rama | Contenido |
|---|---|---|
| 1.3a | `feat/site-settings` | Permisos, `SiteSettings` por API, puente de horarios, estado por sección, limpieza de la web y test de "sin datos hardcodeados" |
| 1.3b | `feat/person-profiles` | `PersonProfile` + `PersonRole`, equipo de Nosotros |
| 1.3c | `feat/visit-page` | Indicaciones y FAQ de Visítanos, preguntas generadas |
| 1.3d | `feat/simple-pages` | Páginas simples sobre el flujo editorial + borrador de la política de privacidad |

Primer paso del tramo 1.3a: commitear este plan (`docs: plan for phase 1.3 (institutional site)`).
Nota: `git fetch`/`push` por SSH falla en esta máquina. Usar HTTPS con `gh` como credential helper:
`git -c credential.helper='!gh auth git-credential' -c url."https://github.com/".insteadOf="git@github.com:" …`.
En worktrees, el pre-push corre con `COMPOSE_PROJECT_NAME=ancla-monorepo`.

### Web (`apps/web`)

- **Utilidades globales nuevas** (cada una en su carpeta, con test):
  - `utils/formatServiceTimes/` (se **mueve** desde `components/SiteStatusScreen/utils/`): recibe
    `ServiceTime[]` + locale y devuelve filas `{ dayLabel, timeLabel, kind }` y textos cortos
    ("Dom · 11:15"). Usa `Intl.DateTimeFormat` para los días.
  - `utils/toOpeningHours/`: `ServiceTime[]` → `"Su 11:15-13:00"` para JSON-LD (solo `worship`).
  - `utils/sectionForPath/`: path (sin locale, vía `stripLocaleFromPath`) → clave de sección o
    `null`. Mapa: `blog → /blog`, `calendar → /calendario-anual` (+ `.ics`), `sermons → /sermones`,
    `ministries → /ministerios`, `visit → /visitanos`.
  - `i18n/utils`: `interpolate(template, values)` con placeholders `{name}`; una clave que falta
    queda visible (`{name}`) y el test lo verifica.
- `middleware.ts`: con `locals.site` resuelve la sección del path. `maintenance` → render de
  `SiteStatusScreen` en variante `section` + 503 (reusar `markSiteOffline`). `outOfService` →
  `rewrite('/404')`. El middleware pasa el locale de la URL a `getSiteConfig(locale)`.
- `Nav`, `Footer`, `sitemap.xml.ts`, `utils/llms.ts`: filtran las entradas de secciones
  `outOfService`.
- **Limpieza de datos** (es/en/pt en el mismo commit): todo string con horario, dirección, email,
  handle o dominio pasa a plantilla con placeholders (`{worshipTime}`, `{bibleSchoolTime}`,
  `{street}`, `{city}`, `{email}`, `{founded}`, `{host}`, `{youtubeHandle}`…), completada desde
  `SiteConfig`. Los handles salen del path de la URL social y el host de `url`. Archivos: `landing`,
  `home`, `nav`, `visit` (solo `where.title` y las FAQ de horario/dirección; el resto de FAQ en
  1.3c), `footer`, `content-pages`, `sermons-page`. Los componentes reciben los datos por props desde
  la sección o la página (Page → Section → Component), no llaman `getSiteConfig` adentro.
  `utils/seo` y el JSON-LD usan `seoDescription`, `toOpeningHours`, address y geo de `SiteConfig`.
- **Test "sin datos de la iglesia"**: `apps/web/src/tests/noHardcodedChurchData/noHardcodedChurchData.test.ts`.
  - Escanea `apps/web/src/**/*.{astro,ts,tsx,json}`, excluye `*.test.ts`, y falla si aparece algún
    fragmento prohibido.
  - Fragmentos: derivados de `SITE_FALLBACK` (email, `address.street`, `postalCode`, lat/lng, host
    de `url`, handles sociales) + extras fijos: `"Herrera"`, `"Arrieta"`, `"11:15"`, `"11h15"`.
  - Allowlist **estrecha**, con un `{ file, fragment, reason }` por entrada. Solo se permiten datos
    que pertenecen a otra fase (`ministriesData.json`/`ministries.json` → 1.5, `data/calendar.ts` →
    1.6) o narrativa fija de D-39 (línea de tiempo de Nosotros, p. ej. el año de fundación dentro de
    la historia). Opus revisa cada entrada.
  - El equipo de Nosotros y las FAQ editables quedan en la allowlist con `reason: "1.3b"` /
    `"1.3c"`, y esos tramos las sacan.
