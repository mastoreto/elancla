# Plan de implementación — 0.1 Rework de la base de datos

Subfase: [`phases/0-foundations/0.1-db-rework.md`](../phases/0-foundations/0.1-db-rework.md).
Estado: **implementado** en la rama `refactor/db-rework` (PR #69). Ver "Resultado" al final.

## Objetivo

Dejar el schema base y sus convenciones listos para que cada feature agregue sus modelos con su
propia migración, sin tener que rehacer nada de lo que se define acá.

**Estrategia**: en 0.1 se **diseñan** las convenciones y se **implementan** solo los modelos base. Los
modelos de cada feature (posts, movimientos, votaciones…) se crean en su subfase siguiendo estas
convenciones. Diseñar todo el schema de una vez y migrarlo vacío generaría tablas que nadie usa
durante meses y que igual cambiarían al implementar cada feature.

## Decisiones que aplica

D-02 (tenant), D-03 (IDs), D-04 (dinero), D-05 (migraciones), D-18/D-51 (monedas y país),
D-21 (Supabase, RLS, roles), D-25 (SiteSettings por organización), D-26 (traducciones).

## Ajustes técnicos detectados al planificar

1. **Prisma 7.10.1**, última versión estable. Prisma 8 todavía es release candidate (`8.0.0-rc.34`):
   no se usa en un sistema contable hasta que salga estable; entonces se evalúa la actualización.
   Prisma 7 ya está probado con Better Auth y Astro en otros proyectos del equipo. Hoy está
   instalado 6.19.3.
   Cambios que trae: generador `prisma-client` con salida explícita, adaptador de driver obligatorio
   (`@prisma/adapter-pg`), URLs de conexión en `prisma.config.ts`, sin binario nativo (simplifica el
   deploy en Vercel y elimina el `external: ['@prisma/client']` de Astro).
2. **Escala de montos** (ajuste a D-04): `Decimal(14,2)` no sirve para monedas con 0 o 3 decimales
   (D-51: yen, dinar kuwaití). Se usa **`Decimal(19,4)`** en BD y el dominio valida la cantidad de
   decimales según la moneda (ISO 4217).
3. **RLS sin depender de `BYPASSRLS`**: en Supabase no está garantizado poder dar ese atributo a un
   rol propio. Se activa RLS en todas las tablas y se crea una política permisiva **solo** para
   `app_runtime`; los roles de la Data API (`anon`, `authenticated`) quedan sin política = sin acceso.
4. **IDs de Better Auth**: configurar `advanced.database.generateId` para que use UUIDv7 (o delegar
   en el default de Prisma); verificar en el paso 4.

## Convenciones del schema (obligatorias desde 0.1)

| Tema | Regla |
|---|---|
| PK | `id String @id @default(uuid(7)) @db.Uuid` |
| Tenant | `organizationId String @db.Uuid` + relación + `@@index([organizationId, …])` en todo modelo de dominio |
| Timestamps | `createdAt DateTime @default(now()) @db.Timestamptz(3)`, `updatedAt @updatedAt @db.Timestamptz(3)` |
| Fechas sin hora | `@db.Date` (fecha de un movimiento, de un evento) |
| Dinero | `Decimal @db.Decimal(19,4)` + `currency String @db.Char(3)` (ISO 4217) |
| Concurrencia | `version Int @default(0)` en entidades editables |
| Borrado | contenido: `deletedAt DateTime?`; tesorería: nunca se borra (anulación) |
| Slugs | `@@unique([organizationId, slug])` (o por traducción) |
| Códigos legibles | `code String` + `@@unique([organizationId, code])`, generado con `DocumentSequence` |
| Traducciones | tabla `XxxTranslation` (`xxxId`, `locale`, campos de texto), `@@unique([xxxId, locale])` |
| Enums | enums de Prisma solo para estados cerrados del sistema; listas editables por el usuario son tablas |
| Nombres | modelos `PascalCase` singular en inglés; tablas `snake_case` plural vía `@@map` |

## Modelos que se implementan en 0.1

```prisma
model Organization {
  id             String   @id @default(uuid(7)) @db.Uuid
  slug           String   @unique
  name           String
  country        String   @db.Char(2)            // ISO 3166-1
  timezone       String                           // IANA, p. ej. America/Montevideo
  defaultLocale  String                           // p. ej. "es"
  locales        String[]                         // habilitados: ["es","en","pt"]
  currencies     String[]                         // ISO 4217: ["UYU","USD"]
  createdAt / updatedAt
}

model DocumentSequence {                          // correlativos sin huecos (D-03)
  organizationId String @db.Uuid
  type           String                           // "MOV", "OC", "SOL", "INV"…
  year           Int
  last           Int    @default(0)
  @@id([organizationId, type, year])
}

model SiteSettings {                              // 1:1 con Organization (deja de ser singleton)
  id             String @id @default(uuid(7)) @db.Uuid
  organizationId String @unique @db.Uuid
  …campos actuales (url, status, contacto, dirección, geo, redes, branding)…
}
model SiteSettingsTranslation { … sin cambios de forma, PK UUID … }

model User / Session / Account / Verification   // Better Auth, PK UUID; `role` se mantiene hasta 0.4
```

Se **eliminan**: `Ministry` y `Movement` stub (vuelven en 1.5 y 2.1
con su forma real), `Author`/`Category`/`Series`/`Post` (vuelven en 1.4 con traducciones),
`ServiceTime` (lo reemplaza `RecurringActivity` en 1.6).

`siteSettings.serviceTimesSummary` se conserva hasta 1.6 para que la web siga mostrando horarios.

## Seguridad de la base

Migración SQL manual (dentro de la carpeta de migraciones, versionada):

1. Roles `app_runtime` (LOGIN, sin DDL) y `app_migrator` (dueño de las tablas).
2. `GRANT SELECT, INSERT, UPDATE, DELETE` sobre las tablas a `app_runtime`; `DEFAULT PRIVILEGES`
   para tablas futuras.
3. `ENABLE ROW LEVEL SECURITY` + `FORCE ROW LEVEL SECURITY` en todas las tablas; política
   `app_runtime_all` (`TO app_runtime USING (true) WITH CHECK (true)`).
4. Revocar todo a `anon` y `authenticated` sobre el schema `public`.
5. Una función de verificación que el test de CI ejecuta (ver Tests).

En local (docker-compose) se crean los mismos roles para que desarrollo y producción se comporten
igual.

## Tests

- La cadena de migraciones aplica desde cero en una BD vacía.
- Toda tabla tiene RLS activado y forzado (consulta a `pg_class`).
- `anon` no puede leer ninguna tabla; `app_runtime` sí.
- Ningún modelo de dominio sin `organizationId` (inspección del DMMF; lista blanca: tablas de Better
  Auth, `Organization`, `DocumentSequence`).
- Ninguna columna de dinero con tipo `Float`/`double precision`.
- Toda PK de modelo es UUID.
- `resolveTranslation`: idioma pedido, fallback al por defecto, sin filas.
- `DocumentSequence`: 50 altas concurrentes → 1..50 sin huecos ni repetidos.

## Fuera de alcance

Modelos de features, `AuditLog` (0.5), roles y permisos (0.4), API (0.2). **Todo se trabaja en
Docker local**; producción (Supabase, Vercel) se resuelve después en 0.8.

## Resultado de la implementación

Cambios respecto de lo planificado:

1. **`User.role` se mantiene hasta 0.4**: el guard de las Server Actions del CRM (PR #67) lo usa;
   sacarlo dejaba sin acceso a los admins.
2. **Roles de Postgres** (`app_migrator`, `app_runtime`) creados por `packages/db/docker/init-roles.sh`
   y no por una migración: crear roles exige superusuario y lleva contraseñas que no deben quedar
   versionadas. Corre solo en un volumen nuevo y se puede re-ejecutar a mano. En producción (0.8)
   se crean con el procedimiento de operación.
3. **RLS sin `FORCE`**: las tablas pertenecen a `app_migrator` (rol de confianza). Lo que se protege
   es el acceso de cualquier otro rol (incluidos los de la Data API de Supabase), que no tiene
   política.
4. **`public.app_secure_tables()`**: activa RLS y crea la política `app_runtime_all` en todas las
   tablas. **Toda migración futura que cree tablas termina con `SELECT public.app_secure_tables();`**.
   El test de invariantes falla si alguna tabla queda sin RLS.
5. **Locales de traducción como texto BCP 47** (no enum), por D-51.
6. **Tests contra la base de Docker local**, limpiando lo que crean; la base de test aislada llega en
   0.7. Los `*.test.ts` se excluyen de `tsc`, igual que en `apps/crm`.
7. **Better Auth**: `advanced.database.generateId: false` (el ID lo pone Prisma con UUIDv7);
   versión fija 1.7.25 en `packages/auth` y `apps/crm`.
8. **Eliminado** `getSiteContent` de `packages/content` (sin consumidores, dependía de
   `ServiceTime`) y los datos de la iglesia hardcodeados en las acciones del CRM.
9. **Prisma 7**: `migrate dev` ya no corre el seed automáticamente; se usa `bun run db:seed`.

Comandos: `db:migrate` (dev), `db:migrate:deploy`, `db:seed`, `db:reset`, `test`.
