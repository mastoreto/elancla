# Plan — Fase 0.4: roles y permisos (RBAC)

## Contexto

0.3 dejó un rol plano (`User.role` = `admin|viewer`, copiado desde `Invitation.role`) y un
`requireAdmin` temporal. La grilla de roles del CRM (`settings/roles`) es un mock con seeds en
`data/`. La 0.4 pone el RBAC definitivo (D-09, D-16, D-20, RF-01, RF-02): catálogo de permisos en
código, roles editables en BD, varios roles por usuario, alcance `own | ministry | all`, política de
sesión por rol y menú del CRM armado desde `GET /me/permissions`.

**Ejecución:** Sonnet 5.5 implementa siguiendo este plan. Después Opus revisa el diff, corre los
tests, prueba en el navegador (Docker local) y **cierra con PR a `develop` con los tests en verde**.

**Rama:** `feat/rbac` desde `develop` una vez mergeado el PR de 0.3 (`feat/auth`). Si 0.3 todavía
no está mergeado, sale de `feat/auth` y se rebasea después. Primer paso: copiar este plan a
`docs/implementation/plans/0.4-rbac.md`.

## Decisiones (tomadas con el usuario)

| Tema | Decisión |
|---|---|
| Ministerios | Se crea ya una tabla `Ministry` **mínima** (`id`, `organizationId`, `name`, `slug`). 1.5 la extiende. |
| Alcance en la grilla | **Por celda**: cada acción concedida tiene su propio alcance. |
| Invitación | Lleva **varios roles** y ministerios opcionales; se asignan al aceptar. |
| Admin | Rol de sistema `key = "admin"`: tiene **todos** los permisos implícitamente (sin filas en `RolePermission`, cubre recursos futuros). No se edita ni se borra. |
| Unión de roles | Permisos = unión; para una misma `recurso:acción` gana el alcance más amplio (`all > ministry > own`). |
| Sesión (D-16) | Gana la más restrictiva: `persistent` = todos los roles lo permiten; duración = mínimo de `maxSessionSeconds` (null = default 30 días). |
| Auditoría | 0.5 todavía no existe: las mutaciones van en `withTransaction` para que 0.5 enchufe `writeAudit` sin reestructurar. |
| Textos del CRM | El CRM no tiene i18n todavía; se sigue el patrón actual (etiquetas en `data/`). |

## Catálogo de permisos (en código, compartido)

`packages/contracts/src/authz/` (lo usan API y CRM, una sola fuente):

- `PERMISSION_CATALOG`: por recurso, acciones válidas y alcances que soporta.
- Acciones: `view | create | edit | approve | delete` (las de la grilla actual).
- Recursos (los módulos actuales de la grilla + los finos):
  `movements, requests, vouchers, projects, budgets, voting, reports, content,
  ministries.profile, ministries.finance, users, roles, invitations, settings`.
- Alcances por recurso: `users, roles, invitations, settings, content` → solo `all`;
  `ministries.*` → `ministry | all`; `requests, projects, vouchers` → `own | ministry | all`;
  el resto → `all` (se amplía cuando su módulo tenga dueño/ministerio).
- Tipos: `Permission = \`${Resource}:${Action}\``, `PermissionScope`, `permissionGrantSchema`
  (zod: `{ resource, action, scope }` validado contra el catálogo).
- `SYSTEM_ROLE_PRESETS`: los 8 roles ESRE + Editor con su grilla inicial (tabla abajo).

### Grilla inicial de los roles sembrados (editable después)

| Rol (`key`) | Permisos |
|---|---|
| Admin (`admin`) | todo (implícito) |
| Tesorero (`treasurer`) | movements, vouchers, requests (incl. approve), budgets, projects, reports, ministries.finance: todo/`all` |
| Síndico (`auditor`) | `view` `all` en todo lo de tesorería + reports |
| Directiva (`board`) | `view` `all` tesorería + reports; projects `create/edit` `all`; requests `approve` `all` |
| Pastoral (`pastoral`) | ministries.profile `view` `all`; requests/reports `view` `all` |
| Líder (`leader`) | requests `view/create/edit` `ministry`; budgets, ministries.finance `view` `ministry`; ministries.profile `view/edit` `ministry` |
| Asamblea (`assembly`) | reports, voting `view` `all` |
| Oficina (`office`) | vouchers `view/create` `all`; movements `view` `all` |
| Editor de contenido (`content-editor`) | content todo `all`; ministries.profile `view/edit` `all` |

## Cambios de BD (`packages/db/prisma/schema.prisma`)

- `Ministry`: `id`, `organizationId`, `name`, `slug`, timestamps; `@@unique([organizationId, slug])`.
- `Role`: `id`, `organizationId`, `key String?` (solo sembrados), `name`, `description`,
  `persistentSession Boolean @default(true)`, `maxSessionSeconds Int?`, timestamps;
  `@@unique([organizationId, key])`, `@@unique([organizationId, name])`.
- `RolePermission`: `roleId` (cascade), `resource`, `action`, `scope`; `@@id([roleId, resource, action])`.
- `UserRole`: `userId`, `roleId` (cascade ambos); `@@id([userId, roleId])`.
- `UserMinistry`: `userId`, `ministryId` (cascade ambos); `@@id([userId, ministryId])`.
- `Invitation`: se quita `role`; se agregan `roleIds String[] @db.Uuid` y `ministryIds String[] @db.Uuid`
  (ponytail: arrays validados al crear; al aceptar se asignan solo los que sigan existiendo).
- `User`: se quita `role`.
- Migración: crea tablas, inserta el rol `admin` por organización y asigna `UserRole` a los usuarios
  con `role = 'admin'`, luego borra las columnas. Los otros 8 roles los crea el seed (idempotente,
  upsert por `(organizationId, key)`) en `packages/db/prisma/seed/` desde `SYSTEM_ROLE_PRESETS`.
- `TENANT_MODELS` (`apps/api/src/core/tenancy/tenantModels/tenantModels.ts`): agregar `Role`, `Ministry`.

## API (`apps/api`)

**`src/core/authz/`** (nuevo)
- `loadAccess(userId, organizationId)`: una consulta → `{ isAdmin, grants: Map<Permission, Scope>,
  ministryIds, sessionPolicy }`. Función pura `mergeGrants()` / `mergeSessionPolicy()` con test.
- `requirePermission(permission)`: middleware; 403 si no hay grant. Deja el alcance en
  `ctx.access`. Se registra en un `WeakSet` de "acceso declarado".
- `allowPublic` y `allowAnySession` (este último = `requireSession`): también se registran en el set.
- `scopeWhere(ctx, permission, { ownerField?, ministryField? })`: `all` → `{}`, `ministry` →
  `{ [ministryField]: { in: ctx.access.ministryIds } }`, `own` → `{ [ownerField]: ctx.user.id }`;
  si el recurso no tiene el campo que pide el alcance → falla cerrado (`where` imposible).
- Policies: `roles.policy.ts` y `users.policy.ts` en sus módulos (protecciones de abajo).

**Contexto** (`core/context/types/types.ts`): `SessionUser` pierde `role`; `AuthenticatedContext`
suma `access`. `requireSession` llama a `loadAccess` y aplica la política de sesión:
si `now - session.createdAt > maxSessionSeconds` → revoca la sesión y 401.

**Sesión no persistente:** plugin Better Auth `roleSessionPolicy` (mismo patrón que
`socialTwoFactorGuard`): hook `after` sobre las rutas que emiten la cookie de sesión
(`/sign-in/email`, `/callback/:id`, `/sign-in/social`, `/two-factor/verify-*`); si la política del
usuario no permite persistencia, reescribe el `Set-Cookie` del token sin `Max-Age`/`Expires`.
Verificar contra Better Auth 1.7.25 y cubrir con test de punta a punta.

**Módulos**
- `modules/identity/roles/`: `GET /roles` (`roles:view`), `GET /roles/:id`, `POST /roles`
  (`roles:create`), `PATCH /roles/:id` (`roles:edit`; reemplaza grants + nombre + política),
  `DELETE /roles/:id` (`roles:delete`; 409 si tiene miembros).
- `modules/identity/users/`: `GET /users` (`users:view`, con roles, ministerios y último acceso),
  `PUT /users/:id/roles` y `PUT /users/:id/ministries` (`users:edit`).
- `modules/ministries/`: `GET /ministries` (`ministries.profile:view`, con `scopeWhere` sobre `id`).
  Solo lectura; el CRUD es de 1.5. El seed crea 2–3 ministerios de prueba.
- `modules/me/`: `GET /me/permissions` (`allowAnySession`) → `{ isAdmin, roles: [{id,name}],
  grants: [{resource, action, scope}], ministryIds }`.
- `invitations`: `requireAdmin` → `requirePermission("invitations:create" | "invitations:view")`;
  body con `roleIds` + `ministryIds`; `invitationGate.markInvitationAccepted` crea `UserRole` y
  `UserMinistry`. Borrar `core/auth/requireAdmin` y `user.additionalFields.role` de `createAuth`.
- Contratos en `packages/contracts/src/{authz,roles,users,ministries}`.

**Protecciones (policies, 409/403)**
- No se puede quitar el último admin (quitar rol `admin` a su último miembro).
- Nadie cambia sus propios roles ni ministerios (403).
- Nadie edita un rol que tiene asignado (evita auto-elevación por la grilla).
- Rol `admin`: no editable ni borrable; los sembrados se pueden editar pero no borrar.
- Grants validados contra el catálogo (acción/alcance no soportado → 400).

## CRM (`apps/crm`)

- `app/(dashboard)/layout.tsx`: pide `/me/permissions` en servidor y lo pasa a un provider de
  cliente; helper `can(access, "movements:view")` en `lib/authz/`.
- `components/app-sidebar.tsx`: cada item declara `requires: Permission`; se filtra. Las páginas
  sin permiso responden `notFound()` (guard en servidor por ruta, helper único).
- `components/sidebar-user-menu.tsx`: muestra los nombres de roles (quitar `ROLE_LABELS` plano).
- `settings/`: conectar a la API y **borrar** `data/roles.ts`, `data/users.ts`,
  `data/invitation-roles.ts`, `data/permission-modules.ts` (el catálogo viene de contracts).
  - `permission-matrix.tsx`: grilla recurso × acción desde el catálogo; **cada celda** = check +
    selector de alcance (solo los alcances que el recurso soporta). Presets se recalculan sobre el
    catálogo (`utils/permissions.ts` + su test se adaptan).
  - `role-form.tsx`: suma política de sesión (persistente sí/no, duración máxima).
  - `users-panel.tsx` / `user-dialog.tsx`: asignar varios roles y ministerios.
  - `invite-dialog.tsx`: multi-rol + ministerios.
  - Tabs de Configuración visibles según permiso.
- Mutaciones vía cliente tipado + `router.refresh()` como ya hace 0.3. Convención de estilos
  `styles` + `cn()` en todo componente tocado.
