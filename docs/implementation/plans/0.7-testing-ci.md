# Plan — Fase 0.7: tests y CI

## Contexto

La 0.7 (D-12, `docs/implementation/phases/0-foundations/0.7-testing-ci.md`) cierra la base: que nada
crítico se rompa sin que CI lo frene. Hoy ya hay mucho hecho y **no se reescribe**:

- `bun test` en `apps/api`, `packages/db`, `packages/contracts`; tarea `test` en `turbo.json`.
- Fixtures con limpieza (`apps/api/test/support/fixtures.ts`), cliente in-process
  (`apiCaller.ts` → `app.request`), matriz de autorización (`authzMatrix.ts` + el test central
  `apps/api/src/core/authz/authzMatrix/authzMatrix.test.ts`), TOTP (`totp.ts`), mailer falso.

Lo que falta: los tests corren contra la **BD de desarrollo** (los `loadEnv.ts` lo marcan con
`ponytail: phase 0.7 brings an isolated test database`), los tests del CRM **no corren** (sin script
`test`), la matriz **no detecta rutas nuevas sin guard**, no hay Playwright, no hay GitHub Actions
ni protección de rama (repo público `mastoreto/elancla`, `main` sin proteger).

**Ejecución: la implementación se hace con Sonnet 5.5** (`claude-sonnet-5-5`), siguiendo este plan
al pie de la letra. Después Opus revisa el diff, corre todo local, verifica el pipeline en el PR y
**cierra con PR a `develop` con tests en verde**, sin `Co-Authored-By`.
**Rama:** `chore/testing-ci` desde `develop` **después** de mergear `feat/storage` (0.6) y
`chore/biome-root-config` (el job de Biome necesita el repo limpio). Si no están mergeadas, sale de
la más reciente y se rebasea. Primer paso: copiar este plan a `docs/implementation/plans/0.7-testing-ci.md`.

## 4. GitHub Actions (`.github/workflows/ci.yml`)

- `on: { pull_request: { branches: [main] }, workflow_dispatch: {} }`. Job guard en todos:
  `if: github.event_name == 'workflow_dispatch' || github.head_ref == 'develop'` (un PR a `main`
  desde otra rama no gasta minutos y queda bloqueado por la protección).
  `concurrency: { group: ci-${{ github.ref }}, cancel-in-progress: true }`; `permissions: contents: read`.
- Pasos comunes: `actions/checkout` (`fetch-depth: 0` en `version`), `oven-sh/setup-bun`
  (`bun-version-file: package.json`), `bun install --frozen-lockfile`. Acciones fijadas por versión mayor.
- **`quality`**: `bunx biome ci .` (sin `--write`) y `bun run check-types`.
- **`db`** (cobertura de BD que hoy CI no tenía): `bun run test:infra` (solo `db-test`) y
  1. `bun run test:db` sobre la BD **vacía**: prueba que todas las migraciones aplican desde cero con
     el rol `app_migrator` y que el seed corre.
  2. Drift: `prisma migrate diff --from-migrations prisma/migrations --to-schema-datamodel prisma/schema.prisma --shadow-database-url <db-test con base shadow> --exit-code`
     (falla si alguien cambió `schema.prisma` sin migración). Script `db:drift` en `packages/db`
     (`app_migrator` tiene `CREATEDB` para la shadow).
  3. `bun run test:db` **otra vez**: `migrate deploy` y seed son idempotentes.
  4. `bun run --filter @ancla/db test` (`schemaInvariants`: RLS, grants de `app_runtime`, audit
     append-only, etc.).
- **`test`**: `bun run test:infra`, `bun run test:db`, `bun run test` (api, db, contracts, crm).
  Si compose se queja por variables del perfil `app`, exportar las de `.env.test` en el job.
- **`e2e`**: igual infra + `bun run test:db`, `bunx playwright install --with-deps chromium`
  (en `apps/crm`), `bun --env-file=.env.test run --filter crm build`, `bun run test:e2e`;
  `actions/upload-artifact` del `playwright-report` con `if: failure()`.
- **`version`**: compara `version` de `package.json` del PR con el último tag `v*` alcanzable desde
  `origin/main`; falla si no es mayor ("corré `bun run release` en develop antes del PR"). Script
  pequeño en `scripts/release/assertVersionBumped/` (con test) usando `Bun.semver.order`.
- Los nombres de job son los checks requeridos: no renombrarlos.

  y lo ejecuta Opus al cierre, con confirmación.

## 6. Husky y panel de consola

- devDependency `husky` (versión fija), script `"prepare": "husky"`. Hooks en `.husky/`, una línea
  cada uno: `bun scripts/hooks/runHook/runHook.ts <pre-commit|commit-msg|pre-push> "$@"`.
- `scripts/hooks/` (cada unidad en su carpeta con barrel):
  - `runSteps/`: recibe `{ title, steps: { label, command: string[], env? }[] }`, corre cada paso con
    `Bun.spawn` capturando stdout/stderr, y dibuja el panel **sin dependencias** (ANSI):
    ```
    ⚓ pre-push · 3 pasos
      ✔ Infra de test (db-test)            2.1s
      ⠹ Tests (api, db, contracts, crm)    41s…
      ○ Build del CRM
    ```
    Spinner braille cada 80 ms con el tiempo transcurrido en vivo; ✔ verde / ✖ rojo con duración;
    al fallar imprime las últimas ~60 líneas de salida del paso, corta los siguientes y termina con
    código ≠ 0 y una línea de ayuda (`bun run check` para Biome; `HUSKY=0 git …` como escape de
    emergencia, documentado). Si `!process.stdout.isTTY` o `NO_COLOR`, salida de líneas simples
    (sin spinner ni colores). Interrumpir con Ctrl-C mata el subproceso.
  - `validateCommitMessage/` (función pura + test): primera línea
    `^(feat|fix|refactor|perf|chore|docs|test|style|build|ci|revert)(\([a-z0-9-]+\))?!?: .+`,
    ≤ 100 caracteres; permite `Merge …` y `Revert "…"`; rechaza cualquier línea
    `Co-Authored-By:` o "Generated with Claude Code". Mensaje de error con un ejemplo válido.
  - `runHook/`: mapea hook → pasos:
    - `pre-commit`: `bunx biome check --staged --no-errors-on-unmatched` (sin `--write`: no toca
      archivos parcialmente staged; el error sugiere `bun run check`) y `bun run check-types`.
    - `commit-msg`: `validateCommitMessage` sobre el archivo `$1` (sin panel de pasos, instantáneo).
    - `pre-push`: `bun run test:infra` (con `--wait` ya es idempotente), `bun run test:db`,
      `bun run test`, `bun run --filter crm build`. Si Docker no responde, falla con un mensaje claro
      ("levantá Docker Desktop / el daemon").
- Tests del `runSteps`: un paso ok y uno que falla (comandos `true`/`false`), verifica orden, corte y
  código de salida (modo no-TTY).

## Verificación

1. Local, desde cero: `bun run test:infra && bun run test:db && bun run test` → todo verde, y la BD
   de dev (5433) no cambia (contar filas de `users` antes/después).
2. Quitar a propósito el `requirePermission` de una ruta (o agregar una ruta dummy) → el test de
   cobertura de la matriz falla nombrando la ruta. Revertir.
3. `bun --env-file=.env.test run --filter crm build && bun run test:e2e` → 4 specs verdes.
4. `bun run check` y `bun run check-types` limpios.
5. Husky: `git commit` con un mensaje inválido → rechazado con ejemplo; con `Co-Authored-By` →
   rechazado; commit válido → se ve el panel con spinner y ✔; `git push` con Docker apagado → error
   claro; con un test roto → ✖ con la salida del test y el push no sale.
6. BD en CI: agregar un campo a `schema.prisma` sin migración → `bun run --filter @ancla/db db:drift`
   falla. Revertir.
7. CI: correr el workflow con `workflow_dispatch` sobre `chore/testing-ci` → `quality`, `db`, `test`,
   `e2e` en verde (`version` puede fallar ahí hasta el release: es lo esperado).
8. PR `chore/testing-ci → develop` (no dispara CI: correcto). Tras el merge, con confirmación del
   usuario, Opus: en `develop` `bun run release:first` → `v0.1.0` + `CHANGELOG.md` →
   `git push --follow-tags` → PR `develop → main` → los 5 jobs en verde.
9. Con confirmación del usuario, aplicar la protección (Opus):
   ```bash
   gh api -X PUT repos/mastoreto/elancla/branches/main/protection --input protection-main.json
   ```
   `main`: `required_status_checks: { strict: true, contexts: ["source-branch","quality","db","test","e2e","version"] }`,
   `required_pull_request_reviews: { required_approving_review_count: 1 }` (aprobación manual del
   PR `develop → main`), `enforce_admins: false`, `allow_force_pushes: false`, `allow_deletions: false`.
   `develop`: `required_status_checks: null`, `required_pull_request_reviews: null`,
   `allow_force_pushes: false`, `allow_deletions: false`. Comprobar que un PR a `main` con check rojo
   muestra "Merging is blocked".
10. Sin `Co-Authored-By` en ningún commit ni PR.
